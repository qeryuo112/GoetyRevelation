# Goety: Neo Revelation — 基于代码审查的移植方案

> 2026-10-12｜Forge 1.20.1 → NeoForge 1.21.1｜方案范围与命名空间已确认。
> 后续状态：P0/P1与P2核心链路已实施验证。本文第3–9节保留最初审查记录；最新执行结果见 `2026-10-12-P2实施与验证.md`（63本地/27真实GameTest通过）。真实双客户端、成品加载与完整后续扩展仍待，不能将历史“未实施”视为当前状态。

## 1. 结论先行

**推荐：以用户提供的完整 jar（外层 Revelation + 内嵌 RevelationFix 4.7）的组合行为为基准，采用“保留业务逻辑、接口定点适配、加载补丁去耦、分模块测试”的渐进移植。**

不能把反编译目录 `decompiled/` 的 93 个 Java 文件直接视为整个模组。它们只是外层。内嵌补丁不仅增加内容，而且会替换外层核心 Mixin、取消旧事件、增加注册项和网络包。只移植外层可以形成另一个较小的基线版本，但不等于移植当前 `2.3.4fix2` 产物。

不是推倒重写；也不是批量把 `net.minecraftforge` 替换成 `net.neoforged` 就结束。继续使用现有 NeoGradle、Java 21、Goety-3 和 Curios 依赖，不为移植再更换构建插件。

本轮已做：阅读规则、入口/物品/实体/事件/数据/客户端/Mixin 与资源对照，逐项核查外层 42 个配置 Mixin 的目标，读取内嵌补丁关键字节码及完整注解，检查现有骨架。未改 `src/` 或构建配置，未提交 Git，未构建或启动游戏，未访问用户游戏实例或 `.minecraft`。

## 3. 会改变路线的实证

### 3.1 RevelationFix 会替换原行为，不能只当可选修复包

补丁 plugin 的 `toRemovedMixins` 含 25 个外层类名，其中 24 个出现在外层配置中。其 LaunchPlugin 在匹配后调用 `clearMixinClass`，清除原 Mixin 的方法、字段和接口，再由补丁实现接管。

因此，静态清理表与配置相交后，外层剩余 18 个配置项不在此清理表；这仍不是已经运行验证的“18 个最终生效 Mixin”，还需检查其他转换与条件启用。

覆盖涉及 `ApostleMixin`、`PlayerMixin`、`LivingEntityMixin`、法术、弓、字体、Boss UI、模型、音乐等核心部分。完整移植的优先阅读源应是补丁的对应实现，外层同名代码只作历史基线，不能同时启用两套逻辑。

证据：`build/revelationfix-bytecode-audit.txt:1045-1184`；`build/revelationfix-extended-audit.txt:118-141`。这两个文件为本地忽略的分析证据，不是公开源文件。

### 3.2 一个注册路径被改名，不是整个命名空间改变

补丁 `gr.ModItemsMixin.modifyRevelationRegistryName` 返回 `revelation`。必须连注解一起看：目标是 `DeferredRegister.register(String, Supplier)`，`ordinal=4`、`index=0`，即第五次注册。

外层第五个物品原注册名为 `wither_quietus_focus`，补丁将其路径改为 `revelation`。**namespace 仍来自原 `ITEMS` 的 `goety_revelation`，不是全局改成 `revelation`。**

本轮曾仅凭方法体误判为 namespace 变化；已用 `javap -v` 更正。后续注册 ID 对照必须读取注解和调用点，不能按方法名字推测。

证据：`decompiled/z1gned/goetyrevelation/item/ModItems.java:9-14`；内嵌 `gr.ModItemsMixin` 的 `@ModifyArg` 注解及字节码。

`GRItems` 还声明 73 个 `RegistryObject` 字段并参与原物品注册；字段数不等于无条件实际注册的精确条目数。配方、模型和注册清单必须结合该初始化逻辑整理。

### 3.3 旧死亡事件被补丁取消

补丁 `gr.LivingDeathListenerFix` 在 `onLivingDeath` HEAD 注入，无条件调用 `ci.cancel()`。不能把外层“下界首次击杀掉落/勋章掉落”的事件原样恢复后宣称保持了 fix2 行为。

补丁也扩展了 `DefeatApollyonInNetherState`。存档字段、一次性奖励规则须按补丁后的实际入口梳理。

证据：`build/revelationfix-bytecode-audit.txt:4501-4564` 及对应注解；外层历史逻辑 `event/LivingDeathListener.java:19-36`。

### 3.4 反编译的配置初始化顺序已失真

`decompiled/.../config/ModConfig.java:11-29` 把 `SPEC = BUILDER.build()` 放在配置项定义前。然而原 class 的 `<clinit>` 是先定义配置项，最后才执行 `BUILDER.build()`。

这属于反编译失真，不应当作原模组的配置 bug。移植时应根据原字节码恢复正确初始化顺序，再写配置读取、默认值、重载测试。补丁又把原默认健康值修改为 666，因此不能直接按外层显示的 560 作为当前产物最终默认值。

证据：`build/outer-bytecode-audit.txt:45-115`；内嵌 `gr.ModConfigMixin` 的健康值替换方法。

**SRG 残留为 0 只能证明可读化覆盖，不证明泛型、作用域命名、静态初始化或控制流等价。** 原始 `decompiled-raw/` 和原 jar 必须保留作对照。参数按序号全局改成 `argN` 还需按作用域检查碰撞。

## 4. 技术选型与模块落点

### 4.1 推荐的目标结构

初期保持一个主 Gradle 工程和一个可运行主模组，不急于拆多个发布 jar。源代码按职责分层：

- `registry`：物品、实体、声音、属性、配方序列化器与数据组件的正常注册。
- `config`：NeoForge 配置加载与重载，恢复初始化顺序。
- `state`：玩家/阿波利翁状态、SavedData、持久化和同步。
- `combat`、`spell`、`goal`：伤害策略、Boss 阶段、法术替换和召唤逻辑。
- `mixin`：必要的 Goety/原版扩展点，按服务端、客户端、可选兼容分配置。
- `client`：UI、模型、渲染层、音乐、Shader，严格限制客户端加载。
- `compat`：Patchouli/Tetra/其他第三方集成，条件注册，不把全部兼容设为硬依赖。

对 `ending_library`：先制作能力依赖表。核心只需要的同步/状态/工具能力可评估用 NeoForge Attachment、payload 和常规 Java 替代；确实不可替代的能力必须单独移植或接入已验证版本。

**后续实施更新**：已拉取用户指定 Mega32K/ending_library 至 `reference/ending_library`，锁定 1.20.1 分支 `562c04751521802939d9ccc8201e7602841bb02b`；本次可见远程分支没有 1.21.1。MIT、2.2.1fix、Forge47.3.12/Java17。内嵌 Fix 733 Java 已可读化；90 个库 import、162 个使用文件全部定位，具体方法/行为逐模块验证。首批正常物品注册/配置不加载整套 Forge 库，隐式掉落保护 tag 单独迁移；完整库能力仍待后续，不为绕过它而默默删功能。

### 4.3 Mixin 原则

- 保留 Goety 私有扩展、Boss/召唤实体初始化等确有需要的 Mixin；按目标方法描述符逐项校验。
- 事件能保持同样时机和语义时优先事件。Goety-3 已有 `StartMagicEvent.setSpell` 与 `GoetyEventFactory.onStartSpell`，可用于法术替换，但须验证不会改变施法、消耗、升级、所有权和附魔效果；不是所有法术注入都能一概删掉。
- 不把补丁“清空旧 Mixin”的 ASM 启动器原样移植。新工程只选择最终有效实现，避免先加载旧代码再运行时清空；第三方兼容隔离。
- 避免沿用极端 priority、脆弱 ordinal 与 `@Overwrite`。但替换前先做行为回归，不能为“更干净”而更改数值。
- 普通 Goety 名称 `remap=false` 与原版成员映射分开处理。NeoForge 1.21.1 的官方名环境不可复用旧 Forge SRG refmap；开发和成品 jar 都要测试。
- 不通过 `require=0`、移除全部 Mixin 或静默捕获异常掩盖核心功能未加载。

## 5. 资源与数据迁移

MC 1.21.1 本地源码已确认：**resource pack format 34，data pack format 48**。不能再把数据包也写成 34。`pack.mcmeta` 的具体输出应按目标加载器对资源/数据的读法设计，并分别验证。

迁移按资源类型进行，不改所有数字和路径就算完工：

1. 原版数据目录按 1.21.1 路径规则转换：`recipes → recipe`、`advancements → advancement`、`loot_tables → loot_table`、`structures → structure`，以及原版 registry 对应的 tag 子目录单数化。`worldgen/structure*` 不是同一条规则，Goety/Fix 自定义目录按它们加载器处理，不盲目全局替换。
2. 108 个配方逐种 serializer 验证。`goety:ritual` 当前 Codec 使用 `ItemStack.STRICT_CODEC`，result 应符合 `id/count/components`；旧 `result.item/nbt` 不能直接复用。旧 `forge:nbt` ingredient 与原始 potion NBT 要迁移到对应组件/自定义 ingredient 类型。
3. 原外层已存在 `revelationfix:equipment_appearance` 配方和 `goety_revelation:enchantment/puzzle` 等 custom ingredient。它们的 serializer 在内嵌补丁注册，不能随资源复制却漏掉对应代码。
4. 先恢复真实注册 ID 清单，再审查配方/标签/战利品/模型引用。无需把 `goety`、`minecraft`、`curios`、`revelationfix` 的引用都改成新 mod id。
5. `forge` tag namespace 及 global loot modifier 加载声明按 NeoForge 与 `c` 公共标签约定逐项转换；不把第三方 tag 或兼容资源当成原版目录自动重写。
6. 外层 50 个结构 NBT 以及补丁追加/覆盖的结构分别建清单。检查 DataVersion、block/entity/item ID 和组件；用新开发测试世界加载、生成并重载。没有实际加载前不宣称结构已兼容。
7. assets 的多数 PNG/音频和基础模型可保留，但 Shader include、GUI 纹理、顶点格式和渲染层按具体差异适配。1.21.1 不应套用更晚版本才引入的全套 item-definition 规范。

实证例子：`decompiled/data/goety_revelation/recipes/enchant/reality_piercer.json:9-15,33-35,41-43` 含 custom enchantment ingredient、`forge:nbt` potion 和 `result.item`；新 Goety `common/crafting/RitualRecipe.java:250-285` 采用 MapCodec 与 StreamCodec，新 `data/goety/recipe/summon_apostle.json:25-27` 使用 `result.id`。

所有原外层 210 个 data JSON 已通过语法解析检查；**JSON 能解析不表示 serializer/registry/schema 验证通过**。

### 6.1 严格遵守 RULES 第 8 条

每次代码或配置改动：

1. 先保存待验证的行为、失败条件或目标 API 断言。
2. 修改后运行对应静态测试/单元测试/资源 Codec 测试或开发 GameTest。Java 测试可以包含编译测试类所需步骤，但这不等于允许提前打发布 jar。
3. 确认测试不为 `NO-SOURCE`，有真实断言、有实际 Mixin 加载/游戏行为覆盖；失败时停止该批。
4. 通过后才执行构建/打包，再单独验证成品运行。

现有 `src/` 没有测试文件。`build.gradle:39-41` 只有 GameTest run 配置，并非已经写好的测试集。第一批应补最小测试设施，而不是用 `./gradlew build` 成功替代测试。
